# Vyaapti: A Deep Dive into the RTGS Risk-Chain Analyzer

## 1. Introduction and High-Level Overview

Vyaapti is a sophisticated, full-stack big data application designed for the real-time detection and analysis of suspicious transaction chains within a Real-Time Gross Settlement (RTGS) system. Its primary objective is to combat financial crimes like money laundering by identifying complex transaction patterns that are often invisible to traditional, rule-based monitoring systems.

The name "Vyaapti" is derived from a Sanskrit word meaning "pervasion" or "omnipresence," reflecting the system's goal of having a comprehensive and all-encompassing view of the transaction network to uncover hidden relationships and illicit activities.

The project is not just a theoretical exercise; it is a well-architected, end-to-end solution that demonstrates the practical application of modern big data technologies to a critical real-world problem. It covers the entire data lifecycle, from raw data ingestion and processing to advanced analytics, machine learning, and intuitive visualization.

This document provides a deep dive into the technical architecture, design decisions, and implementation details of the Vyaapti project.

## 2. System Architecture and End-to-End Data Flow

The architecture of Vyaapti is designed for scalability, performance, and modularity. It follows a multi-layered approach, with each layer responsible for a specific set of tasks.

### 2.1. Architectural Layers

The system can be broken down into the following logical layers:

1.  **Data Ingestion Layer:** This is the entry point for raw transaction data into the system. In a real-world scenario, this layer would connect to a streaming platform like Apache Kafka or a message queue to receive transactions in real time. For the purpose of this project, data is either generated or read from a CSV file.

2.  **Data Processing Layer (Apache Spark):** This is the analytical core of the system. Apache Spark is used for its ability to perform large-scale, in-memory data processing. This layer is responsible for:
    *   Transforming raw transaction data into a graph structure.
    *   Applying graph algorithms to detect suspicious chains.
    *   Enriching the data with calculated features and risk scores.
    *   Running machine learning models for account clustering.

3.  **Data Persistence Layer (Cassandra / DataStax Astra):** The results of the data processing layer, along with the raw and processed data, are stored in a highly scalable, distributed NoSQL database. Cassandra is chosen for its excellent write performance and linear scalability, which are essential for handling the high volume of data generated by financial systems. The project is configured to use DataStax Astra, a cloud-native Cassandra-as-a-Service, which simplifies deployment and management.

4.  **Backend API Layer (Node.js & Express):** This layer provides a RESTful API that acts as an intermediary between the frontend and the database. It exposes endpoints for the frontend to query the processed data, such as fetching detected chains, account details, and dashboard summaries.

5.  **Presentation Layer (Frontend):** This is the user-facing part of the application. It's a web-based dashboard that provides an intuitive interface for analysts to explore the data, visualize transaction chains, and gain insights from the analytics.

### 2.2. End-to-End Data Flow

Here is a step-by-step walkthrough of the data flow through the Vyaapti system:

1.  **Transaction Generation/Ingestion:** The process begins with transaction data. The `spark-jobs/chain-builder/generate-transactions.py` script can be used to create a synthetic dataset of transactions, including patterns designed to be detected by the system.

2.  **Spark Job Execution:** The `spark-jobs/chain-builder/detect_chains_astra.py` Spark job is executed. This is the main data processing step.

3.  **Data Loading:** The Spark job loads the transaction data from the `transactions_processed` table in Cassandra (or from a CSV file as a fallback).

4.  **Graph Construction:** The transaction data, which consists of `from_account`, `to_account`, and `amount`, is used to construct a directed graph in memory using the `NetworkX` library. Each account is a node, and each transaction is a directed edge between two nodes.

5.  **Chain Detection:** The Spark job traverses the graph to find simple paths between nodes. A "chain" is a sequence of transactions that form a path. The algorithm looks for paths of a certain length (e.g., 2-4 hops).

6.  **Feature Engineering and Risk Scoring:** For each detected chain, a set of features is calculated, including:
    *   `total_value`: The sum of all transaction amounts in the chain.
    *   `num_hops`: The number of transactions in the chain.
    *   `time_span`: The time difference between the first and last transaction.
    *   `velocity`: The total value divided by the time span.

A custom risk scoring algorithm is then applied to each chain based on these features and other patterns (e.g., circular transactions, layering).

7.  **Data Persistence:** The detected chains, along with their features and risk scores, are written back to the `chains` table in Cassandra. The relationship between accounts and chains is stored in the `account_chains` junction table.

8.  **Frontend Request:** A user opens the Vyaapti web dashboard in their browser. The frontend JavaScript makes API calls to the Node.js backend to fetch data.

9.  **Backend API Handling:** The Node.js backend receives the request. For example, a `GET /api/chains` request is handled by the `chainController.js`.

10. **Database Query:** The backend controller queries the Cassandra database to retrieve the requested data. For example, it might execute `SELECT * FROM chains` to get all the detected chains.

11. **API Response:** The backend formats the data from Cassandra into a JSON response and sends it back to the frontend.

12. **Frontend Rendering:** The frontend JavaScript receives the JSON data and dynamically renders it on the page. For example, it populates the "Top Risky Accounts" table, draws the charts using Chart.js, and visualizes transaction networks using vis-network.js.

## 3. Database Schema and Data Modeling (Cassandra)

The choice of Cassandra as the database is a key architectural decision. Cassandra is a distributed, wide-column NoSQL database designed for high availability and scalability with no single point of failure. Its data modeling is based on the queries that need to be performed, a concept known as "query-driven design."

The schema for the Vyaapti project is defined in `cassandra/schema-astra.cql`.

### 3.1. Tables

The database consists of several tables, each designed for a specific purpose:

*   **`chains`**: This is the primary table for storing the results of the chain detection process.
    *   `chain_id` (UUID, PRIMARY KEY): A unique identifier for each detected chain.
    *   `accounts` (list<text>): An ordered list of account IDs in the chain.
    *   `total_value` (double): The total value of all transactions in the chain.
    *   `num_hops` (int): The number of transactions (edges) in the chain.
    *   `risk_score` (double): The calculated risk score for the chain (0-100).
    *   `flags` (map<text, boolean>): A map of flags indicating the type of risk detected (e.g., `{'circular': true, 'rapid': true}`).
    *   `status` (text): The current status of the chain (e.g., 'active', 'under_investigation', 'closed').

*   **`accounts`**: This table stores information about each individual account.
    *   `account_id` (text, PRIMARY KEY): The unique identifier for the account.
    *   `cluster_label` (int): The cluster this account belongs to, as determined by the K-Means algorithm.
    *   `suspicion_index` (double): A risk score for the individual account.
    *   Other calculated features like `mean_amount`, `frequency`, `velocity`.

*   **`account_chains`**: This is a junction table to model the many-to-many relationship between accounts and chains.
    *   `account_id` (text): The account ID.
    *   `chain_id` (UUID): The chain ID.
    *   `role` (text): The role of the account in the chain (e.g., 'originator', 'intermediary', 'destination').
    *   PRIMARY KEY (`account_id`, `chain_id`): This composite primary key allows for efficient lookups of all chains an account is involved in.

*   **`transactions_processed`**: This table stores the raw transaction data after it has been processed.
    *   `txn_id` (UUID, PRIMARY KEY): A unique identifier for the transaction.
    *   `from_account` (text): The source account.
    *   `to_account` (text): The destination account.
    *   `amount` (double): The transaction amount.
    *   `timestamp` (timestamp): The time of the transaction.

*   **`risk_features`**, **`clustering_results`**, **`audit_log`**: These tables are also defined in the schema and are intended for storing more detailed features, clustering model results, and audit trails, respectively.

### 3.2. Data Modeling Considerations

*   **Denormalization:** The `chains` table contains a list of accounts. This is a form of denormalization, which is a common practice in Cassandra to optimize for read performance. Instead of having to join tables to get the accounts in a chain, they are stored directly with the chain data.
*   **Query-Driven Design:** The `account_chains` table is a perfect example of query-driven design. It is designed to answer the question: "What chains is a given account a part of?". The primary key is chosen to make this query very efficient.

## 4. Data Processing and Analytics (Apache Spark)

The heart of the Vyaapti system's intelligence lies in its data processing pipeline, which is implemented as an Apache Spark job. The main script for this is `spark-jobs/chain-builder/detect_chains_astra.py`.

### 4.1. Spark Session Initialization

The script begins by creating a Spark session and configuring it to connect to DataStax Astra:

```python
spark = SparkSession.builder \
    .appName("RTGS-ChainDetector") \
    .config("spark.jars.packages",
            "com.datastax.spark:spark-cassandra-connector_2.12:3.2.0") \
    .config("spark.cassandra.connection.config.cloud.path",
            ASTRA_SECURE_BUNDLE) \
    .config("spark.cassandra.auth.username", ASTRA_CLIENT_ID) \
    .config("spark.cassandra.auth.password", ASTRA_CLIENT_SECRET) \
    .getOrCreate()
```

*   `spark.jars.packages`: This tells Spark to download the DataStax Spark Cassandra Connector, which is necessary for reading from and writing to Cassandra.
*   The other configuration options provide the credentials and secure connect bundle for authenticating with Astra DB.

### 4.2. Graph Construction

The core of the chain detection process is to model the transactions as a graph. The script loads the transactions and uses the `NetworkX` library to build a directed graph (`nx.DiGraph`):

```python
edges = transactions_df.select(...).collect()

G = nx.DiGraph()

for e in edges:
    G.add_edge(
        e.source,
        e.target,
        amount=float(e.amount),
        timestamp=e.timestamp,
        txn_id=str(e.txn_id)
    )
```

This code iterates through each transaction and adds an edge to the graph from the source account to the target account. The edge itself contains attributes like the transaction amount and timestamp.

### 4.3. Chain Detection Algorithm

The `detect_chains` function is where the actual chain detection happens. It uses `nx.all_simple_paths` to find all paths between pairs of nodes in the graph, up to a certain cutoff length (`MAX_HOPS`).

To optimize this process and avoid exploring the entire graph (which can be computationally expensive), the algorithm focuses on "high-degree nodes" - nodes with a large number of incoming and outgoing transactions. The assumption is that these are more likely to be part of interesting chains.

```python
high_degree_nodes = sorted(
    nodes,
    key=lambda n: graph.degree(n),
    reverse=True
)[:HIGH_DEGREE_NODE_LIMIT]

for source in high_degree_nodes:
    # ...
    for target in nodes:
        # ...
        for path in nx.all_simple_paths(
                graph,
                source,
                target,
                cutoff=MAX_HOPS
        ):
            if len(path) >= MIN_HOPS + 1:
                chains.append(path)
```

### 4.4. Risk Scoring Algorithm

Once a chain (a path) is detected, the `calculate_risk_score` function is called to assign a risk score. This is a heuristic-based algorithm that combines several risk factors:

```python
def calculate_risk_score(f):
    score = 0
    flags = {}

    if f["accounts"][0] == f["accounts"][-1]:  # Circular transaction
        score += 30
        flags["circular"] = True

    if f["velocity"] > 10_000_000:  # Rapid succession
        score += 25
        flags["rapid"] = True

    if f["num_hops"] >= 4:  # Layering
        score += 20
        flags["layering"] = True

    # ... other rules for structuring and time compression ...

    return min(score, 100), flags
```

This algorithm is a key piece of the project's intellectual property. It translates qualitative red flags from anti-money laundering (AML) regulations into a quantitative risk score.

## 5. Machine Learning Integration

Vyaapti integrates machine learning to enhance its analytical capabilities. The primary ML components are K-Means clustering for account segmentation and a Random Forest classifier for risk prediction. The training script for the classifier is `ml-models/classification/random_forest_risk.py`.

### 5.1. K-Means Clustering

Although the training script for K-Means is not shown in the provided files, the database schema and other scripts indicate that accounts are clustered into groups based on their transactional behavior. This is a form of unsupervised learning that can help identify accounts with similar characteristics. For example, one cluster might represent "high-volume traders," while another might be "infrequent, low-value transactors." This can help analysts focus their attention on unusual activity within a cluster.

### 5.2. Random Forest Classifier

The `random_forest_risk.py` script trains a Random Forest model to predict the risk level of an account.

*   **Features:** The model is trained on a set of features that describe an account's behavior, such as:
    *   `mean_amount`: The average transaction amount.
    *   `frequency`: The number of transactions.
    *   `velocity`: The rate at which money moves through the account.
    *   `diversity_score`: A measure of how many different counterparties the account transacts with.
    *   `cluster_label`: The cluster the account belongs to (from K-Means).

*   **Labels:** The risk levels (`Low`, `Medium`, `High`, `Critical`) are created based on the `suspicion_index` of the account. This means the Random Forest is being trained to learn the relationship between the account's features and its heuristic-based risk score, effectively creating a predictive model that can score new accounts automatically.

*   **Training Process:**
    1.  Data is fetched from the `accounts` table in Cassandra.
    2.  The features are standardized using `StandardScaler`.
    3.  The data is split into training and testing sets.
    4.  A `RandomForestClassifier` is trained on the training data.
    5.  The model's performance is evaluated on the test data.
    6.  The trained model (`rf_classifier.pkl`), the scaler (`rf_scaler.pkl`), and the list of features (`rf_features.pkl`) are saved to disk using `joblib`.

## 6. Backend API (Node.js and Express)

The backend is a standard Node.js application using the Express web framework. Its main purpose is to serve as a bridge between the frontend and the database.

### 6.1. Server Setup (`server.js`)

*   **Dependencies:** It uses `express` for the web server, `cors` to handle cross-origin requests from the frontend, and `cassandra-driver` to connect to the database.
*   **Middleware:** It sets up middleware for CORS and for parsing JSON request bodies.
*   **Database Connection:** It initializes the connection to the DataStax Astra database.
*   **Routing:** It imports and uses the route handlers from the `routes/` directory.

### 6.2. Routes and Controllers

The API is organized using a typical routes-and-controllers pattern:

*   **Routes (`routes/`):** Files like `accountRoutes.js` define the API endpoints. For example:
    ```javascript
    // GET /api/accounts/top - Get top suspicious accounts
    router.get('/accounts/top', accountController.getTopAccounts);

    // GET /api/account/:accountId - Get account by ID
    router.get('/account/:accountId', accountController.getAccountById);
    ```

*   **Controllers (`controllers/`):** Files like `accountController.js` contain the business logic for handling requests. They execute the necessary database queries and format the response. For example, the `getAccountById` function:
    ```javascript
    const getAccountById = async (req, res) => {
        try {
            const accountId = req.params.accountId;
            const query = 'SELECT * FROM accounts WHERE account_id = ?';
            const result = await client.execute(query, [accountId]);

            if (result.rows.length === 0) {
                return res.status(404).json({ error: 'Account not found' });
            }

            res.json(result.rows[0]);
        } catch (error) {
            res.status(500).json({ error: 'Failed to fetch account details' });
        }
    };
    ```

## 7. Frontend Interface (HTML, CSS, JavaScript)

The frontend is a single-page style application built with plain HTML, CSS, and JavaScript. It's designed to be a functional and visually appealing dashboard for financial analysts.

### 7.1. Structure and Design

*   **HTML:** The project has several HTML files, one for each "page" of the application (e.g., `index.html` for the main dashboard, `chains.html` for the list of chains).
*   **CSS:** The styling in `style.css` implements a modern "glassmorphism" design, characterized by frosted-glass effects, background blurs, and gradient animations. This gives the application a premium and professional look.
*   **JavaScript (`scripts/`):** The application's logic is in the `scripts/` directory. Each page has its own JavaScript file (e.g., `main.js` for the dashboard). Each page has its own JavaScript file (e.g., `main.js` for the dashboard).

### 7.2. Key Frontend Features

*   **Dynamic Data Loading:** The JavaScript files make extensive use of the `fetch` API to call the backend, retrieve data, and dynamically update the content of the page without requiring a full page reload.
*   **Interactive Charts (Chart.js):** The dashboard features a doughnut chart for risk score distribution and a line chart for transaction volume trends. These are created using the Chart.js library.
*   **Network Visualization (vis-network.js):** The `graph.html` page (and its corresponding `graph.js`) uses the `vis-network.js` library to render interactive, physics-based network graphs of the transaction chains. This is a powerful tool for visualizing the flow of money between accounts.
*   **Component-like Structure:** The JavaScript code is organized into functions that handle specific parts of the page (e.g., `updateStats`, `loadTopAccounts`, `createRiskChart`), which mimics a component-based approach.
